# 0601 学生端功能开发日志

## 2026-06-01

### 1. 建立开发日志

- 做了什么：新增本文档，用于记录本次三个学生端功能的实际开发过程。
- 原因：用户要求记录开发日志，且本次涉及前端、后端、数据库三类改动，需要保留实现依据和影响范围。
- 效果：后续每个关键改动都会记录“做了什么、为什么做、产生了什么效果”。

### 2. 新增后端 DTO

- 做了什么：新增 `StudentCourseQueryRequest` 和 `CourseDropRequestCreateRequest`。
- 原因：课程筛选需要承载老师名称、课程名、课程号、课程种类、学分、星期、节次等查询条件；退课申请需要独立接收教学班编号和退课原因。
- 效果：Controller 可以用结构化对象接收查询参数和申请参数，避免继续扩散散乱参数。

### 3. 扩展学生端后端接口

- 做了什么：改造 `GET /api/student/courses/available` 支持筛选；新增已选课程、可退课程、直接退课、提交退课申请、查询退课申请接口。
- 原因：三个功能分别需要课程筛选查询、独立已选课程数据源、退课页面数据源和退课操作入口。
- 效果：学生端前端可以通过 `student.js` 统一调用新接口；退课写操作进入 Service 事务，并把数据库触发器错误转换为业务提示。

### 4. 新增退课数据库脚本

- 做了什么：新增 `sql/0601_student_features.sql`，包含 `teaching_class.course_start_date`、`course_drop_request` 表和三个触发器。
- 原因：退课规则要求由触发器约束；现有教学班表没有明确开课日期，必须增加稳定字段，避免解析 `week_range` 字符串。
- 效果：执行脚本后，数据库会限制一周内直接退课、三周内提交申请、超过三周禁止申请；退课成功后自动维护教学班已选人数。

### 5. 扩展前端 API

- 做了什么：修改 `getAvailableCourses(params)` 支持查询参数，新增已选课程、退课课程、直接退课、退课申请相关 API 函数。
- 原因：页面不直接写 Axios 请求，学生端接口需要统一收敛在 `frontend/src/api/student.js`。
- 效果：三个功能页面都可以复用统一 API 层，后续调整接口路径时改动范围更小。

### 6. 改造学生选课页面

- 做了什么：在 `StudentCourseView.vue` 增加老师名称、课程名、课程号、课程种类、学分、星期、节次筛选表单，并展示课程号和课程种类。
- 原因：用户要求支持三种直接查询和三种间接查询；现有表格缺少课程号、课程种类，不利于核对查询结果。
- 效果：学生可在选课页组合查询课程，点击重置后恢复默认可选课程列表。

### 7. 新增已选课程页面

- 做了什么：新增 `StudentSelectedCourseView.vue`，上方展示当前已选课程课表，下方展示已选课程列表。
- 原因：用户要求“已选课程”独立展示，且点击后先看到现有课表，再看到列表。
- 效果：学生能在独立页面同时查看课表分布和已选课程明细。

### 8. 新增退课页面

- 做了什么：新增 `StudentDropCourseView.vue`，展示当前已选课程、直接退课按钮、申请退课按钮和我的退课申请列表。
- 原因：用户要求新增退课按钮并进入退课界面，页面需要根据退课状态区分直接退课、提交申请和不可退课。
- 效果：学生可在页面直接发起退课或提交退课申请；待审核申请会显示审核状态。

### 9. 新增路由和菜单

- 做了什么：在 `router/index.js` 注册 `/student/selected-courses` 和 `/student/drop-courses`，并在侧边栏新增“已选课程”“退课”菜单。
- 原因：新增页面需要可访问入口，并且仅学生角色可见。
- 效果：学生登录后可以从侧边栏进入两个新功能页面。

### 10. 兼容细分节次筛选和现有数据

- 做了什么：后端课程时间筛选兼容 `1-2节/3-4节` 命中数据库现有 `1-4节`，`5-6节/7-8节` 命中 `5-8节`，`9-10节/11-12节` 命中 `9-12节`。
- 原因：本次文档新增了更细的节次时间，但当前 `school.sql` 样例数据仍按半天块保存节次，直接等值查询会导致筛选无结果。
- 效果：前端按新节次查询时，可以命中现有教学班数据；后续如果数据库改成细分节次，等值查询仍然可用。

- 效果：学生可以提交退课申请并查看审核状态；后续需要继续开发教师端、管理员端审核接口和页面后，双审核自动退课流程才能完整闭环。

### 14. 优化退课确认交互

- 做了什么：直接退课确认框取消时显式返回，不继续执行后续逻辑。
- 原因：用户取消确认属于正常操作，不应该在浏览器控制台留下未处理的 Promise reject。
- 效果：取消退课确认后页面保持静默，只有确认后才调用退课接口。

### 16. 修正学生端接口报错

- 做了什么：将前端已选课程查询从 `GET /student/course-selections` 改为 `GET /student/selected-courses`；将退课申请前端调用从 `/student/course-drop-requests` 改为 `/student/drop-requests`，后端保留原路径并新增别名路径。
- 原因：用户反馈点击已选/选课相关入口出现 `Request method 'GET' is not supported`，退课页出现 `No static resource api/student/course-drop-requests`。更明确的别名路径可以避免 GET 与 POST 同路径造成混淆，也能避开已报错的旧路径。
- 效果：前端不再对 `course-selections` 发 GET，也不再调用 `course-drop-requests` 作为学生端申请列表路径；后端同时兼容新旧路径。

### 17. 补齐教师端退课审核

- 做了什么：新增教师退课审核 DTO、Mapper、Service、Controller、API 和页面 `TeacherDropRequestView.vue`。
- 原因：退课申请需要任课教师审核，教师只能审核自己授课教学班的退课申请。
- 效果：教师菜单新增“退课审核”；教师可以查看本人课程相关退课申请，并执行通过或驳回。若教师和管理员均通过，后端会自动尝试执行退课。

### 18. 补齐管理员端退课审核

- 做了什么：新增管理员退课审核 DTO、Mapper、Service、Controller、API 和页面 `AdminDropRequestView.vue`。
- 原因：退课申请需要管理员和教师双审核，管理员端必须具备查看全部退课申请和审核能力。
- 效果：管理员菜单新增“退课审核”；管理员可以审核所有退课申请。若教师和管理员均通过，后端会自动更新选课记录为 `已退`，并由数据库触发器维护人数和时间约束。
